회원가입부터 개인기억 보호까지

아이디는 사람이 기억하기 위한 이름이고, UUID는 시스템이 신뢰하는 실제 신원입니다. JWT가 그 UUID를 매 요청에 증명하고, Supabase RLS가 데이터베이스에서 마지막 접근 경계를 만듭니다.

← 기억 서랍으로 가입·로그인 JWT RLS 역할 스키마
01

한 요청이 지나가는 길

BROWSER

가입 또는 로그인

사용자는 아이디·이메일·비밀번호를 입력합니다. 비밀번호는 브라우저 저장소에 보관하지 않습니다.

POST /api/signup
POST /api/login
FASTAPI

입력 검증

admin 예약 여부, 아이디 형식과 요청을 검증하고 Supabase Auth에 인증을 요청합니다.

username → email lookup
SUPABASE AUTH

UUID와 JWT 발급

비밀번호를 검증하고 사용자의 불변 UUID를 sub에 담은 서명된 Access JWT를 발급합니다.

auth.users.id = JWT.sub
FASTAPI

사용자 권한으로 요청

JWT를 검증한 뒤 같은 Bearer JWT로 사용자 범위의 데이터베이스 요청을 보냅니다.

Authorization: Bearer <JWT>
POSTGRES RLS

행 단위 차단

공유기억과 JWT UUID가 소유한 개인기억만 반환합니다. 다른 사람의 개인 행은 보이지 않습니다.

auth.uid() = owner_user_id
모든 사용자가 보는 공유기억+현재 UUID가 소유한 개인기억
02

일반 가입과 관리자 생성은 경로가 다릅니다

일반 회원가입

공개 화면에서는 일반 사용자만 생성합니다. 관리자 권한을 요청 본문으로 선택할 수 없습니다.

  1. 브라우저가 { username, email, password }를 전송합니다.
  2. FastAPI가 예약 아이디 admin과 중복·형식을 검증합니다.
  3. Supabase Auth가 UUID 사용자를 만들고 프로필에 아이디를 연결합니다.
  4. 이메일 확인 설정이 켜져 있으면 확인 안내를, 즉시 세션이면 앱 화면을 보여줍니다.
비밀번호는 account_profiles나 기억 테이블에 저장되지 않습니다.

초기 관리자 admin

서버를 관리할 수 있는 사람이 터미널에서 한 번 부트스트랩합니다.

python scripts/bootstrap_admin.py --email 실제메일@example.com
  1. 비밀번호를 터미널에서 숨김 입력하며 파일이나 명령 기록에 넣지 않습니다.
  2. 서버 전용 Service Key로 Auth 사용자를 생성합니다. 같은 이메일의 기존 계정이 정확히 하나면 UUID를 유지한 채 승격합니다.
  3. username='admin', app_role='admin', 이메일 확인 상태를 설정합니다.
  4. account_profiles가 로그인 아이디 admin을 실제 이메일에 매핑합니다.
일반 회원가입 API에서 admin은 항상 거부됩니다.
03

JWT는 서명된 사용자 출입증입니다

읽을 수 있지만 고칠 수는 없습니다

JWT 내용은 암호문이 아니므로 비밀을 넣지 않습니다. 대신 Supabase 서명이 붙어 있어 UUID나 역할을 바꾸면 검증에 실패합니다.

HEADERPAYLOADSIGNATURE
Access JWT와 Refresh Token은 JavaScript가 읽지 못하는 HttpOnly 쿠키로 전달합니다. 운영에서는 HTTPS와 Secure 쿠키가 필요합니다.
{
  "sub": "7c52…-사용자-UUID",
  "role": "authenticated",
  "app_metadata": {
    "app_role": "editor"
  },
  "exp": 1786200000
}
04

RLS가 개인기억을 행 단위로 격리합니다

scope = 'shared'
OR (
  scope = 'personal'
  AND owner_user_id = auth.uid()  -- JWT.sub
)

공유기억

로그인한 모든 계정이 검색하고 답변 근거로 사용할 수 있습니다.

내 개인기억

owner_user_id가 현재 JWT UUID와 같을 때만 사용할 수 있습니다.

남의 개인기억

검색 결과가 아니라 데이터베이스 조회 단계에서 제외됩니다. 관리자도 예외가 아닙니다.

05

역할은 기능을, UUID는 소유권을 결정합니다

viewer공유 + 본인 개인불가불가없음

auth.users

  • app_metadataapp_role
1 : 1↔id

  • idUUID · PK/FK
  • usernameUNIQUE

  • created_attimestamp
1 : N→UUID

public.memories

  • idUUID · PK
  • scopeshared | personal
  • owner_user_id개인 소유자
  • created_by_user_id작성자
  • embeddingvector
아이디나 이메일이 바뀌어도 auth.users.id UUID는 유지되므로 기억 소유권이 흔들리지 않습니다.
사용자가 바꿀 수 있는 user_metadata.username은 표시 이름이나 권한 판정에 쓰지 않습니다. FastAPI는 인증된 UUID로 비공개 account_profiles를 다시 조회합니다.
07

보안 경계 체크

브라우저

HttpOnly 토큰은 JavaScript에서 읽지 못합니다. 로컬 저장소에는 사용자 UUID별 질문·답변만 두고, 검색 근거의 전체 원문은 저장하지 않습니다.

RLS

FastAPI 필터가 실수하더라도 PostgreSQL이 auth.uid()로 다른 개인 행을 한 번 더 차단합니다.

서버 전용 비밀

SUPABASE_SERVICE_KEY와 OPENAI_API_KEY는 RLS 우회·외부 과금 권한이 있으므로 절대 공유하거나 브라우저에 보내지 않습니다.

기억 입력

OpenAI API 키처럼 보이는 문자열은 저장 전에 거부하고, 과거 키 행은 검색 대상에서 격리합니다. 노출된 키는 즉시 폐기·재발급합니다.

이 문서는 현재 기억 서랍의 인증·권한·데이터 경계를 설명하는 정적 기술 시각화입니다.
